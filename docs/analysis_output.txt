        3 -> 5 pairs: 510.78 cycles per pair
        5 -> 9 pairs: 510.78 cycles per pair
      line through the multi-pair arms: +0.0 + 510.78 * pairs
      -> the intercept is zero to within 0.0 cycles, which is
         the structural check: k pairs cost exactly k times one pair,
         with nothing left over, as an additive per-pair cost requires.

      Extrapolated to the shipped arm: 510.8, measured 446.9
      -> the lone shipped pair is -63.8 cycles (-12.5%) below the line.

      But this is NOT a privileged first pair. If pair #1 were
      intrinsically 447 and every later pair 511, the
      multi-pair totals would have to be:
        3 pairs: model 1468  measured 1532  off by +64
        5 pairs: model 2490  measured 2554  off by +64
        9 pairs: model 4533  measured 4597  off by +64
      A constant miss at every arm. The discount does not persist,
      so in an arm with three or more pairs EVERY pair costs
      511 including the first.

      Honest statement: a LONE pair costs 447 cycles; with three
      or more in flight each costs 511. Pair cost depends on how
      many pairs there are, not on which one it is -- an allocator
      state or load effect (more live chunks, more splitting, a
      larger free-list working set), not a position effect.

      CONSEQUENCE: the shipped configuration has exactly one pair,
      so 447 is the number to quote. 511 belongs to a regime
      the shipped code is never in, and calibrating the shipped
      pair from it would overstate by 14%.

    (excluded from the line: pairs=[8] -- that arm is so slow it
     never left a 64-packet burst, so its own slope is not measurable)

    weighted fit   C = 262 + 365 * pairs
     pairs     measured      line   residual   sigma
         0    255.7 +/-13       261.9       -6.3    -0.5
         1    717.6 +/-42       627.4       90.2     2.2
         3   1330.5 +/-73      1358.2      -27.7    -0.4
         5   2066.1 +/-56      2089.0      -22.9    -0.4
    chi-square 5.3 on 2 dof   p = 0.07235
    -> consistent with one price per pair
       (R-squared is deliberately not quoted for this regression.
        With this few points and this x-range it is near-1 whatever
        happens, and it says nothing about whether the residuals
        are consistent with the error bars -- which is the only
        question that matters here.)
    -> an INCREMENTAL pair costs 365 cycles = 174 ns

    The two estimators disagree on the incremental pair --
    511 cycles from the matched-burst slopes against 365
    from the fit -- and the
    reason is visible in P, which is not constant across the arms:
      -1:89  +0:88  +2:97  +4:99
    P rises 10 cycles from the hoisted arm to the deepest
    usable one. The matched-burst estimator multiplies the whole
    per-packet difference by 64 and so charges that rise to the
    per-burst term; the fit separates them but pays for it with a
    model. The truth is bracketed, not pinned: an incremental pair
    costs between 365 and 511 cycles.
    Why P moves at all is not established. A once-per-burst
    allocation should not touch per-packet cost; cache and TLB
    pollution from the allocator's own chunk walking is the
    obvious candidate and has not been measured.

    NONE OF THIS MOVES THE HEADLINE. The shipped pair is 447
    cycles by matched burst and 462 by the fit difference, and the
    non-allocator remainder is measured directly at 256 +/- 13.
    The allocator is ~60-64% of the per-burst cost on either route.

    non-allocator per-burst cost, measured directly by the
    hoisted arm: 256 +/- 13 cycles
    (NOT the fitted intercept -- that is an extrapolation, and
     where the line is rejected it is a wrong one.)

    depth 8 -> 64:  P 115.8 -> 87.7   C 375.4 -> 717.6

    Model-free check -- cost at matched burst, since P and C are
    strongly anti-correlated in this fit and a claim about either
    alone is fragile. A real slope difference shows up as a crossing:
                B=64          B=32          B=16           B=9
   d8     121.7+/-2.6    127.5+/-2.3    139.3+/-2.5    157.5+/-4.1 
   d16    107.6+/-0.7    117.7+/-0.6    137.9+/-0.8    169.4+/-1.5 
   d32    102.7+/-0.7    114.1+/-0.6    137.1+/-0.7    172.7+/-1.4 
   d64     98.9+/-1.8    110.1+/-1.5    132.5+/-1.6    167.4+/-3.2 
    A pipeline-ramp C must fall with depth while P rises.
    An allocator C must be flat in depth.

    Sharper, using the measured allocator cost. Exactly one
    alloc/free pair runs per burst at EVERY depth -- the buffer is
    sized by the burst length, not by the queue depth (dramblast.c
    :243), so the -Q knob does not change what is allocated. That
    makes 447 cycles a FLOOR under C at every depth, and the
    remaining 271 of the shipped C (718) is all the
    pipeline ramp can possibly own.

    The test is a floor, not a spread: C may rise with depth
    without limit, but no arm's C may fall below the allocator's
    own per-burst cost.
      depth  8: C =  375.4 +/- 49   below the floor by 72 (1.5 sigma)
      depth 16: C =  646.5 +/- 18   OK
      depth 32: C =  733.7 +/- 18   OK
      depth 64: C =  717.6 +/- 42   OK
    -> not falsified, but the headroom is gone: at the
       shallowest depth the non-allocator part of C is
       consistent with zero, which is what a ramp that
       scales with queue depth would look like.

  At a MATCHED queue count, q=1 -> q=6 (the two arms cover
  different ranges, so the percentages above are not comparable):
    dramblast  walk cycles  +20.3   cost +12   reaching the cost: 59%
    maglev     walk cycles  +11.8   cost  +0   reaching the cost: 0%
    -> the engine that is already waiting absorbs the extra walk
       time; the one retiring at IPC 3.4 has no slack to hide it
       in. That is the opposite direction from the prefetch
       result, and for a consistent reason: a pipeline hides
       latency it ISSUED EARLY, not latency added underneath it.

  CONCLUSION: the core-count term that breaks the burst model on
  4 KiB pages is contention for shared page-table structures. It is
  measured in the DURATION of a walk, not in how many walks happen,
  and it vanishes entirely on 1 GiB pages where there are none.
  No new runs were needed -- the counters were already in the logs.
